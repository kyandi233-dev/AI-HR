# 实验流程

本文档按操作顺序说明：从打开终端，到跑完一批实验、查看结果、上传 GitHub。
研究设计见 `研究协议与限制.md`，各部分功能见项目 `README.md`，字段含义见 `数据字段.md`。

## 1. 先理解三层配置

| 层       | 负责什么                                     | 位置                            |
| -------- | -------------------------------------------- | ------------------------------- |
| 实验代码 | 条件、材料、提示词的组装                     | 各阶段的 `run.py` 或脚本      |
| 模型参数 | 模型、温度、thinking、max_tokens、超时、并发 | 各阶段 `config/settings.json` |
| 批次计划 | 跑哪个任务、批次名、阶段、次数、材料版本     | 各阶段 `config/*.json`        |

- **运行器：** `shared/cli.py` 读取三层配置，负责预览、调用 API、存档和导出。
- **改实验逻辑：** 改实验代码。
- **改模型参数：** 改 `settings.json`。
- **改批次安排：** 改计划 JSON，或用命令行参数覆盖。

## 2. 环境准备（每台设备一次）

1. 打开 PowerShell，进入项目根目录：

```powershell
Set-Location "你的路径"
```

2. 新设备建虚拟环境并安装依赖：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

3. 激活虚拟环境（可选，只影响当前终端窗口）：

```powershell
.\.venv\Scripts\Activate.ps1
```

- 激活后提示符带 `(.venv)`，可以直接用 `python`。
- 不激活时，用完整路径 `.\.venv\Scripts\python.exe` 代替 `python`。
- 两种写法效果相同。

4. 填密钥：编辑项目根目录 `.env`：

```dotenv
DEEPSEEK_API_KEY=你的密钥
```

- 保存一次即可，后续各次实验共用。
- `.env` 已被 Git 忽略，不会上传。

5. 运行离线测试（不调用 API）：

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

## 3. 一次批次的完整流程

### 第 1 步：选实验，读它的 README

- 实验1：`experiments/exp_1_principles/README.md`
- 材料准备：`material_preparation/README.md`
- 实验2：`experiments/exp_2_material_evaluation/README.md`
- 实验3：`experiments/exp_3_hiring/README.md`

### 第 2 步：确定批次计划 JSON

- 每个实验目录已有一份示例计划，例如实验1 的 `config/principles_100.json`。
- 计划 JSON 是普通文本文件，用编辑器打开、复制、修改即可。
- 也可以不新建文件，直接在命令行覆盖字段；计划文件主要用于留档和复现。

### 第 3 步：定 run_id（批次名）

- `run_id` 是这批实验的名字，也是结果文件夹名。
- 每个新批次必须用新名字，不能和已有批次重复。
- 已有批次目录在 `results/<run_id>/`，可以直接查看。

### 第 4 步：预览（不调用 API、不花钱）

```powershell
python experiments/exp_1_principles/run.py
```

- 会显示：任务、阶段、计划数、待运行数、模型、参数、并发、批次名，以及第一条完整提示词。
- 不发送请求、不写结果文件。

### 第 5 步：正式执行（调用 API、写文件、花钱）

```powershell
python experiments/exp_1_principles/run.py --execute
```

- 每个试次发送一条完整 user 消息，不携带历史对话。
- 结果保存到 `experiments/exp_1_principles/results/<run_id>/`。

### 第 6 步：查看结果

```text
results/<run_id>/
├── batch.json     ← 本批参数和试次清单
├── results.csv    ← 每次调用一行
└── records/       ← 逐次输入和输出 JSON
```

- `results.csv` 看整体：状态、条件、模型、token、两道题的答案。
- `records/` 看原始证据：完整提示词、原始响应、校验结果、错误信息。

### 第 7 步：失败补跑

```powershell
python experiments/exp_1_principles/run.py --execute --retry-failed
```

- 只重试失败或中断的试次，不重复成功项。
- 重试记为 `a02` 等新尝试，原记录保留。

### 第 8 步：上传 GitHub（如果需要）

```powershell
git add -f experiments/exp_1_principles/results/<run_id>
git add experiments/exp_1_principles/results/principles_all_results.csv
git commit -m "添加原则实验结果（单条 user 消息，无 system 消息）"
git push origin main
```

- 结果目录默认被 `.gitignore` 忽略，所以要加 `-f` 强制添加。
- 只上传需要保留的批次，不要上传 `.env`、`.venv` 和 `backups/`。

### 第 9 步：记录

- 更新 `docs/更新记录.md`。
- 在批次目录放一份 `README.md`，写明批次名、阶段、参数、消息结构、成功数和失败数。

## 4. 批次计划 JSON 怎么写

### 常用字段

| 字段                  | 含义                    | 示例                             |
| --------------------- | ----------------------- | -------------------------------- |
| `task`              | 跑哪个任务              | `principles`                   |
| `run_id`            | 批次名，也是结果目录名  | `20261118_principles_pilot_01` |
| `stage`             | 用途标签                | `pilot`                        |
| `repeat`            | 每个条件重复次数        | `25`                           |
| `occupations`       | 需要职业的任务填写      | `["software_developer"]`       |
| `materials_version` | 实验2、3 固定的材料版本 | `pilot_materials_v1`           |
| `profile_overrides` | 临时覆盖模型参数        | `{"temperature": 1.0}`         |

- 其余可用字段：`count`、`start_index`、`source`、`foundation`、`concurrency`。
- `profile_overrides` 只能覆盖 `model`、`temperature`、`thinking`、`max_tokens`。

### 一个完整示例

```json
{
  "task": "principles",
  "run_id": "20261118_principles_pilot_02",
  "stage": "pilot",
  "repeat": 25,
  "occupations": []
}
```

- `repeat=25` 表示每条件 25 次；实验1 有四个条件，共 100 次调用。

### 什么时候新建 JSON

| 情况                      | 做法                                                             |
| ------------------------- | ---------------------------------------------------------------- |
| 同一实验，再跑一批        | 不新建；运行时用 `--run-id` 换新名字                           |
| 同一实验，换规模或条件    | 复制一份新 JSON，改 `repeat` 等字段，运行时用 `--batch` 指定 |
| 新的实验类型（新的 task） | 建新实验目录和新计划 JSON                                        |

- **同一份 JSON 可以反复用：** 它只是默认值；每批用 `--run-id` 区分即可。
- **不同规模建议各存一份 JSON：** 例如 `principles_100.json` 和 `principles_400.json`，方便回溯。
- **运行指定计划：**

```powershell
python experiments/exp_1_principles/run.py --batch experiments/exp_1_principles/config/principles_400.json --execute
```

### 参数优先级

- **命令行显式参数 > 批次计划 JSON > 程序默认值。**
- 命令行能覆盖的常用字段：`--task`、`--run-id`、`--stage`、`--repeat`、`--concurrency`、`--limit`、`--batch`、`--occupations`、`--materials-version`。

## 5. run_id 规则

- **允许字符：** 字母、数字、下划线、短横线，以字母或数字开头。
- **用途：** 结果目录名、批次标识、分析时的分组依据。
- **必须唯一：** 同一 `run_id` 重复运行会跳过已成功项。
- **建议格式：** `日期_实验_用途_序号`，例如 `20261118_principles_main_01`。
- **改提示词、材料或模型参数后：** 必须用新 `run_id`，程序会拒绝在旧批次上续跑变化后的输入。

## 6. stage 规则

- **`development`：** 开发调试，验证流程，不用于分析。
- **`pilot`：** 预实验，检查失败率、回答分布、参数是否合适。
- **`main`：** 正式数据，用于最终分析。
- **stage 只是标签：** 不改变模型参数，只记录在 `batch.json`、每次输入输出和 `results.csv` 中。
- **分析时：** 按 `stage` 列筛选。

## 7. `--execute` 与常用参数注意事项

| 参数                    | 作用              | 注意                                        |
| ----------------------- | ----------------- | ------------------------------------------- |
| 不加 `--execute`      | 预览              | 不调用 API、不花钱、不写文件                |
| `--execute`           | 正式执行          | 调用真实 API、写文件、产生费用              |
| `--run-id`            | 指定批次名        | 必须是新名字，否则跳过                      |
| `--stage`             | 指定用途标签      | `development` / `pilot` / `main`      |
| `--batch`             | 指定计划 JSON     | 不写则用该实验的默认计划                    |
| `--concurrency`       | 同时请求数        | 默认读 `settings.json` 的 `concurrency` |
| `--limit`             | 本次最多新跑几个  | 只影响本次，不改变批次计划                  |
| `--retry-failed`      | 只重试失败/中断项 | 会新增 `a02` 等尝试编号                   |
| `--occupations`       | 选择职业          | 实验2、3需要，实验1不需要                   |
| `--materials-version` | 指定固定材料版本  | 实验2、3需要                                |

- **默认是预览，是本项目的有意安全设计：** 防止误触一次产生 100 次付费调用。
- **真实跑之前先看预览输出：** 核对阶段、次数、模型、温度、`max_tokens`、并发和批次名。
- **同一批次不要边跑边改提示词、材料或参数。**
- **不要手工修改 `results/` 里的文件：** 原始记录用于追溯。
- **不要把 `.env`、`.venv`、`backups/` 提交到 Git。**
- **历史批次不要续跑：** 新实验一律新 `run_id`。

## 8. 结果文件说明

| 文件                               | 内容                                                |
| ---------------------------------- | --------------------------------------------------- |
| `batch.json`                     | 批次名、阶段、参数、并发、100 个试次的输入摘要      |
| `results.csv`                    | 每次尝试一行：状态、条件、模型、token、两道题的答案 |
| `records/*.input.json`           | 完整提示词、参数、元数据、请求哈希                  |
| `records/*.output.json`          | 原始响应、回答正文、解析结果、用量、错误、质量提示  |
| `results/<任务>_all_results.csv` | 该任务所有批次的汇总表                              |

- **成功条件：** `finish_reason=stop`、JSON 可解析、字段范围正确、理由非空。
- **失败记录：** `status=error`，保留原始响应和错误信息，不自动重填。
- **质量提示：** 题目键顺序与要求不同时写入 `validation_warnings`。

## 9. GitHub 上传与大小限制

- **默认不上传：** 结果目录被 `.gitignore` 忽略。
- **手动上传：** `git add -f results/<run_id>` 强制添加。
- **单文件 50 MiB：** Git 会警告，但仍可推送。
- **单文件 100 MiB：** GitHub 阻止。
- **网页界面上传：** 单文件最大 25 MiB。
- **仓库大小：** 建议小于 1 GB，强烈建议小于 5 GB。
- **实测体积：** 原则实验 100 次约 1 MB（202 个文件）。
- **估算方法：** 每个试次约 10 KB，1000 次约 10 MB。
- **官方说明：** [https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)

## 11. 运行前 / 运行后检查清单

### 运行前

- `.env` 里密钥可读。
- 预览显示的阶段、数量、模型、温度、`max_tokens`、并发、批次名符合预期。
- `run_id` 是新的，没有和已有批次重复。
- 知道本批会调用多少次、大概花多少费用。
- Git 工作区状态明确，避免结果和代码改动混在一起。

### 运行后

- 看“执行结束”行的成功、失败、跳过数量。
- 打开 `results.csv` 确认行数和列值。
- 查看 `status=error` 的记录和 `error_message`。
- 确认批次体积，记录是否需要上传。
- 更新 `docs/更新记录.md`。

## 12. 常见问题

- **为什么默认是预览？** 防止误触产生付费调用；正式跑加 `--execute`。
- **同一 run_id 再跑会怎样？** 成功项跳过；失败项需要 `--retry-failed`。
- **改了提示词还能续跑吗？** 不能；程序会拒绝，换新 `run_id`。
- **为什么结果不在 Git 里？** 默认忽略，避免仓库膨胀；需要时手动 `git add -f`。
- **为什么没有 system 消息？** 本设计每次只发送一条 user 消息，所有指令和材料都在其中；四个条件只在定义顺序和问题顺序上不同。
- **可以不写计划 JSON 吗？** 可以，命令行参数能覆盖全部常用字段；计划文件用于留档和复现。
