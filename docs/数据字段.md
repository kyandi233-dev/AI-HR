# 数据字段与存档结构

## 输出文件（每个职业和任务单独）

`results/<occupation>/<phase>/runs/<run-id>/<task-id>/`

或公共任务：`results/_principles/...`、`results/_morality/...`。

## 记录单位与命名规范

- `results/` 是所有输出的根目录，不代表某一次运行。
- `run-id` 是一个配置和计划固定的实验批次。一个批次可分多次命令续跑；启动一次命令不等于新增一个批次或重复。
- `task-id` 是批次内的一次完整 API 请求及其回复。唯一标识由任务目录、`run-id`、`task-id` 共同组成；原则调查的一条记录同时包含 `task1` 和 `task2`，不是每个问题各发一次请求。
- `record.json` 的 `run_id` 标记批次，`record_unit=api_request` 标记保存单位；`context.condition` 和 `context.repeat` 标记条件及重复编号。CSV 对应列为 `run_id`、`record_unit`、`meta_condition`、`meta_repeat`。旧记录导出时从目录补齐批次和记录单位，不改写原文件。

新批次建议命名为 `<YYYYMMDD>_<task>_<stage>_<batch>`，例如 `20261116_principles_pilot_01`。`stage` 使用 `pilot`（预实验）或 `main`（正式实验）；日期为批次建立日（统一使用 UTC），末尾为同日批次序号。此为推荐规范；程序仍兼容原有批次名，仅允许字母、数字、下划线和短横线，最长 49 字符。实际调用时间以记录中的 UTC 时间为准。

原则调查的单次请求目录沿用 `<condition>_T<repeat>`，例如 `M12_T01`：`M` 表示私人道德信息先定义，`A` 表示专业能力信息先定义；`12/21` 是两个问题的呈现顺序；`T01` 是该条件第 1 次独立重复（至少两位，不是问题编号）。

```text
results/_principles/principles/runs/
  20261116_principles_pilot_01/       一个实验批次
    manifest.json                   整批计划
    M12_T01/                        M12 条件，第 1 次完整请求
      request.json
      raw_response.json
      answer.txt
      parsed.json
      record.json
    M21_T01/
    A12_T01/
    A21_T01/
```

目录内采用固定文件名，由父目录标明批次、条件与重复次数，避免人工重命名破坏程序续跑和导出。`results/all_results.csv` 是可重新生成的全局汇总表，每次导出会更新；不能作为某个批次唯一的原始存档。

执行 `python src/hrpilot.py export` 时，也会在每个批次目录生成 `<run-id>.csv`，例如 `20261116_principles_pilot_01/20261116_principles_pilot_01.csv`。该表汇总本批次所有独立会话，每次调用尝试一行；原则调查同一行的 `result_task1`、`result_task2` 分别保存两个问题的结果（JSON 文本）。两题属于同一条回复，不能当作两次独立会话。

批次不以终端开启时间或某次命令为界：同一批次暂停后续跑仍写入同一份批次 CSV，使用新 `run-id` 才分成另一份。导出会重新生成批次 CSV，不追加重复行；原始请求和回复继续分别保存在各 `task-id` 目录。若人工重试，历史失败尝试也作为行保留，`attempt_archive` 为历史尝试的归档时间，当前记录该字段为空；统计有效结果时应筛选 `status=ok`。

每个条件、每个重复均使用全新会话，不携带其他条件、以前的问题回复或评分历史。原则调查的两个问题在同一份完整提示词中一次提出；跨条件共享会话、同一会话内反复追问均不属于当前设计。

## 单次请求内的文件

- `manifest.json`（在 `runs/<run-id>/`）：冻结本批计划中**所有** task_id、输入摘要、模型参数和程序版本摘要；部分运行后再续跑必须保持一致。
- `request.json`：本条请求的完整单条 user 消息（含角色、规则、材料和输出要求）、当前调用参数；不含 API Key。
- `raw_response.json`：完整的 API 响应，包含返回模型名、`system_fingerprint`、用量、finish_reason 等可获得信息。
- `answer.txt`：逐字保存模型回答内容。
- `parsed.json`：仅 JSON 模式且校验通过时保存解析结果。
- `record.json`：批次 `run_id`、记录单位 `record_unit`、状态 `ok/error`、任务、完整输入 hash、Prompt hash、生成时间 UTC、程序/SDK版本、错误类型等。
- `failed_attempts/`：人工明确重试时保留上次失败尝试的原始记录。

`results/all_results.csv`：用 `export` 从各目录合并的便于浏览的汇总表。这个 CSV 不能替代原始记录。

## 任务名称

| 任务 | 含义 | 存放位置 |
|---|---|---|
| jd | 由 O*NET 职业资料生成 JD | 每职业 jd_generation |
| resume | 由确认 JD 生成独立简历草稿 | 每职业 resume_generation |
| resume-review | 审核简历自然性/一致性 | 每职业 resume_review |
| moral-generate | 生成背景故事组（B/C） | _morality/moral-generate |
| moral-check | 故事道德效价/基础分类等（不依赖职业） | _morality/moral-check |
| moral-relevance | 故事与具体职业 JD 的直接专业关联 | 每职业 moral_relevance |
| principles | 无具体职业的四种顺序原则调查 | _principles/principles |
| baseline | 通过审核的 JD+简历，A 先导评分 | 每职业 baseline |
| abc | 正式 A/B/C | 每职业 abc |

## 主要评分键

**招聘评价**：`education_fit`、`work_experience`、`professional_skills`、`accomplishments`、`overall_suitability`（均 1–5 整数）、`interview_probability`（0–100 整数）、`reason`（文本）。

**原则调查**：`task1` / `task2`，每项含 `priority`、`weight_ability`、`weight_morality`（和为100）、`importance_ability`、`importance_morality`（1–7）、`reason`。条件 M12/M21/A12/A21 按定义顺序与任务顺序定义；输出保留任务标识。

**道德检验**：`moral_valence`、`moral_foundations`、`comprehensibility`、`naturalness`；与 JD 直接专业关联的 `direct_professional_relevance` 单独存在于 `moral-relevance` 阶段。

**配对材料**：`pair_id`、`foundation`、`neutral`、`negative`。背景类型在内部 metadata 中标记；招聘模型看不到这些标签。

## 关于 JSON 输出

官方 JSON 模式保证语法上合法 JSON，但不保证字段、数值或分值范围正确。程序会在解析后进行第二道检查；不合格记录保存原始回答并标记 `error`。所有 JSON 示例中的数值使用 `null`，尽量避免以示例分值诱导评分。
