# 数据字段与存档结构

## 每批一个目录

原则调查保存于 `results/principles/<run-id>/`；道德材料任务位于 `results/morality/<task>/<run-id>/`；职业任务位于 `results/<occupation>/<phase>/<run-id>/`。没有 `runs/` 层，也不再为每次对话创建文件夹。

```text
results/principles/20261116_principles_pilot_02/
  manifest.json
  requests.jsonl
  responses.jsonl
  records.jsonl
  20261116_principles_pilot_02.csv
  run_summary.json                 本批另附的人工整理运行摘要
  migration.json                   从旧格式迁移的来源和校验信息
```

## 记录单位与命名规范

- `run-id` 是配置和计划固定的实验批次，可以分多次命令续跑。新批次建议命名为 `<YYYYMMDD>_<task>_<stage>_<batch>`，例如 `20261116_principles_pilot_02`。日期统一使用 UTC；`pilot` 表示预实验，`main` 表示正式实验。批次名允许字母、数字、下划线和短横线，最长 49 字符。
- `task_id` 标记批次内的一项测量，例如 `M12_T01`：M/A 表示道德/能力定义先介绍，12/21 表示问题顺序，T01 表示该条件第 1 次独立重复。编号存入 JSONL 和 CSV，不作为文件夹名。
- `attempt` 从 1 开始标记同一项测量的调用尝试次数。失败后的人工重试使用新的 attempt；原失败行保留。唯一键为任务目录、run_id、task_id、attempt。
- 每个条件、每个重复都使用全新会话，只发送一条完整 user 消息，不携带历史。原则调查一次请求同时回答 task1/task2；--repeat N 对每个条件的完整提示词独立重复 N 次，共 4N 次请求。

## 批次文件

JSONL 每一行是一个独立 JSON 对象。不同文件用相同的 `task_id`、`attempt` 关联。

| 文件 | 内容 |
|---|---|
| `manifest.json` | 整批计划：任务、职业、run_id、模型参数、全部测量的摘要及程序 SHA256。续跑必须一致 |
| `requests.jsonl` | 每次调用前写入 `{task_id, attempt, request}`；request 包含完整消息、参数和接口地址，不含密钥 |
| `responses.jsonl` | 接口返回后写入 `{task_id, attempt, raw_response, answer}`；保留完整 API 响应及逐字回答。接口未返回时没有对应响应行 |
| `records.jsonl` | 每次完成或失败后写入原有状态、条件、重复编号、UTC 时间、模型、版本、用量、输入摘要及错误信息，同时增加 attempt 和 parsed（校验通过的答案；没有时为 null） |
| `<run-id>.csv` | export 生成的本批汇总，每次调用尝试一行；不加 `_results` 后缀 |
| `run_summary.json` | 可选运行摘要；不会由 export 自动更新 |
| `migration.json` | 可选迁移说明，保存旧文件的 SHA256；不改变实验发生时的时间、程序摘要或模型记录 |

`results/all_results.csv` 汇总全部批次。CSV 的 `run_id`、`task_id`、`attempt`、`meta_condition`、`meta_repeat` 标记来源；`result_task1`、`result_task2` 保存两题的 JSON 答案。两题属于同一条回复，不作为两次独立会话。统计有效答案时筛选 `status=ok`。

export 会重新生成 CSV，不追加重复行。JSONL 原始记录仅追加，成功记录续跑时跳过；失败记录需显式 `--retry-failed` 才重试。若请求已保存但程序中断，程序也不会自动重发，以免重复计费。不要让多个进程同时写入同一个批次。

## 旧数据迁移

```bash
python src/hrpilot.py migrate-results
```

该命令不调用 API：先在项目外 `/workspace/.archives/AI-HR/`（本地运行时为项目父目录下的 `.archives/AI-HR/`）创建并校验原文件压缩备份，再将旧的逐次目录合并为 JSONL，逐条核对完整请求、原始响应、回答、解析值和失败历史。验证成功后移除旧批次目录，并重新导出 CSV。目标目录已存在时停止，不覆盖文件。

迁移保留原 manifest、时间、模型、用量和程序摘要，不把旧实验标记成新运行。程序改动后进行新实验应使用新的 run-id。export 也兼容尚未迁移的旧目录；同一批次的实际续跑必须先迁移。已进入 Git 的原始记录继续保留在 Git 历史中。

## 任务名称

| 任务 | 含义 | 存放位置 |
|---|---|---|
| jd | 由 O*NET 职业资料生成 JD | 每职业 jd_generation |
| resume | 由确认 JD 生成独立简历草稿 | 每职业 resume_generation |
| resume-review | 审核简历自然性/一致性 | 每职业 resume_review |
| moral-generate | 生成背景故事组（B/C） | morality/moral-generate |
| moral-check | 故事道德效价/基础分类等（不依赖职业） | morality/moral-check |
| moral-relevance | 故事与具体职业 JD 的直接专业关联 | 每职业 moral_relevance |
| principles | 无具体职业的四种顺序原则调查 | principles |
| baseline | 通过审核的 JD+简历，A 先导评分 | 每职业 baseline |
| abc | 正式 A/B/C | 每职业 abc |

## 主要评分键

**招聘评价**：`education_fit`、`work_experience`、`professional_skills`、`accomplishments`、`overall_suitability`（均 1–5 整数）、`interview_probability`（0–100 整数）、`reason`（文本）。

**原则调查**：`task1` / `task2`，每项含 `priority`、`weight_ability`、`weight_morality`（和为100）、`importance_ability`、`importance_morality`（1–7）、`reason`。条件 M12/M21/A12/A21 按定义顺序与任务顺序定义；输出保留任务标识。

**道德检验**：`moral_valence`、`moral_foundations`、`comprehensibility`、`naturalness`；与 JD 直接专业关联的 `direct_professional_relevance` 单独存在于 `moral-relevance` 阶段。

**配对材料**：`pair_id`、`foundation`、`neutral`、`negative`。背景类型在内部 metadata 中标记；招聘模型看不到这些标签。

## 关于 JSON 输出

官方 JSON 模式保证语法上合法 JSON，但不保证字段、数值或分值范围正确。程序会在解析后进行第二道检查；不合格记录保存原始回答并标记 `error`。所有 JSON 示例中的数值使用 `null`，尽量避免以示例分值诱导评分。
