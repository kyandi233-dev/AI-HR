# 数据与存档

本文档定义实验材料版本、批次记录及输出字段。运行命令参见[运行指南](运行指南.md)；变量操作化与分析逻辑参见[研究设计](研究设计.md)。

## 1. 材料与结果目录

| 类型 | 目录 |
|---|---|
| 材料草稿与批准版本 | `material_preparation/drafts/`、`material_preparation/approved/` |
| 实验2固定材料 | `experiments/exp_2_material_evaluation/materials/<版本>/` |
| 实验3固定材料 | `experiments/exp_3_hiring/materials/<版本>/` |
| 实验1原则判断 | `experiments/exp_1_principles/results/<run_id>/` |
| 实验2道德属性 | `experiments/exp_2_material_evaluation/results/morality/<run_id>/` |
| 实验2岗位关联性 | `experiments/exp_2_material_evaluation/results/relevance/<职业ID>/<run_id>/` |
| 实验3单独A | `experiments/exp_3_hiring/results/a_only/<职业ID>/<run_id>/` |
| 实验3 A/B/C | `experiments/exp_3_hiring/results/abc/<职业ID>/<run_id>/` |
| 材料生成与审核 | `material_preparation/results/<任务>/<职业ID（如适用）>/<run_id>/` |

**材料快照**：`manifest.json` 保存所属实验、版本、来源、文件清单及 SHA256。运行时验证文件清单与内容；同名版本不被覆盖。实验2与实验3分别保存自己的版本副本，数据不能仅凭相同版本名认定为同一份材料。

## 2. 批次记录结构

~~~text
<run_id>/
  batch.json
  results.csv
  records/
    <task_id>_a01.input.json
    <task_id>_a01.output.json
    <task_id>_a02.input.json
    <task_id>_a02.output.json
~~~

- **`batch.json`**：任务、阶段、计划规模、模型配置、材料快照标识、试次列表和协议摘要。
- **`*.input.json`**：完整请求消息、配置、任务标识、开始时间、并发设置与请求摘要。
- **`*.output.json`**：原始 API 响应、回答正文、解析结果、验证警告、状态、错误信息、实际模型和 token 用量。
- **`results.csv`**：根据逐次记录生成的可读表格，每次请求尝试占一行；失败与重试仍保留在表内。
- **任务汇总表**：同一任务类型的跨批次结果保存在对应 `results/` 根目录的 `*_all_results.csv`。

历史迁移批次可保留不同的文件布局，其原始记录位于 `legacy/`。新批次按当前结构生成。

## 3. 主要字段

| 类别 | 字段 | 含义 |
|---|---|---|
| 批次 | `run_id`、`stage`、`task`、`task_id` | 批次、用途、任务类型及试次编号 |
| 调用 | `attempt`、`repeat`、`sequence`、`timestamp_utc` | 尝试序号、重复序号、计划顺序及开始时间 |
| 材料 | `occupation`、`resume_id`、`pair_id`、`background_type`、`condition` | 职业、简历、故事与实验条件 |
| 版本 | `materials_version`、`materials_sha256` | 固定材料版本及清单摘要 |
| 模型 | `requested_model`、`returned_model`、`temperature`、`thinking`、`max_tokens` | 请求与实际返回的模型信息及采样配置 |
| 用量 | `prompt_tokens`、`completion_tokens`、`total_tokens` | API 报告的输入、输出及总 token |
| 状态 | `status`、`finish_reason`、`error_message`、`validation_warnings` | 有效性、结束原因、失败信息及质量提示 |

当前实验2/3并未在全部逐次记录中单独保存预设 `foundation` 字段；如需按六类道德基础汇总，应通过对应材料版本中的 `pair_id` 与故事文件匹配，不可仅凭编号名称推断。

### 实验结果字段

- **实验1**：`task1_*` 与 `task2_*` 各包含 `priority`、`weight_ability`、`weight_morality`、`importance_ability`、`importance_morality`、`reason`。
- **实验2道德属性**：`moral_valence`、`moral_foundations`、`comprehensibility`、`naturalness`。
- **实验2岗位关联性**：`direct_professional_relevance`。
- **实验3招聘评价**：`education_fit`、`work_experience`、`professional_skills`、`accomplishments`、`overall_suitability`、`interview_probability`、`reason`。
- **材料审核**：简历质量审核保存 `naturalness`、`professional_plausibility` 等字段；其含义与实验3的能力评分不同。

## 4. 响应状态及数据选择

| 状态 | 含义 | 分析处理 |
|---|---|---|
| `ok` | 当前任务的结果通过解析和字段范围检查 | 进入候选有效样本，仍需按阶段筛选 |
| `error` | 调用、结束原因、解析、校验或草稿写入失败 | 保留原始证据，不作为有效评分 |
| `interrupted` | 已登记输入，但缺少完整最终输出 | 按运行指南检查并决定是否重试 |

- **重复尝试**：`attempt=a01` 为首次尝试；后续重试产生 `a02` 等。若分析以试次为单位，必须先确定每个试次采用哪一次有效尝试，避免重复计数。
- **批次用途**：`development`、`pilot`、`main` 由研究者指定。仅凭状态 `ok` 不能判断记录是否属于正式数据。
- **顺序警告**：原则实验回答顺序与要求不同时，结果可仍为 `ok`，顺序差异记录于 `validation_warnings`。
- **拒答**：当前程序尚无独立拒答分类字段；不能将所有 `error` 自动解释为模型拒答。

## 5. 分析时的数据对应关系

- **同一简历**：以 `occupation` 与 `resume_id` 标识。
- **B/C 配对**：在同一简历、`pair_id` 和重复标识下比较两种行为背景。
- **A 共享**：同一简历的 A 结果对应多个 B/C 故事配对；展开数据时不能将同一个 A 当作多个独立观测。
- **预筛与正式数据**：单独 `baseline` 批次可用于简历预评估，正式 `abc` 应独立采集 A/B/C；使用 `run_id` 与 `stage` 区分。
- **跨职业比较**：必须保留职业、材料版本及调用配置，并核对是否使用同一研究设计。

## 6. 版本追溯

- **请求一致性**：同一批次检查试次计划、输入内容和模型参数，防止改变材料后继续写入原批次。
- **程序来源**：每次尝试保存 `program_sha256`；批次文件保存关键模块的协议摘要。
- **结果导出**：CSV 可由原始输入输出重新生成；不得通过编辑原始 `input.json` 或 `output.json` 调整分析结果。
- **外部存储**：结果目录默认不自动纳入 Git；按需提交特定批次，遵守根目录 README 中的存储与密钥管理规则。
