# 材料生成记录怎么读

`material_preparation/results` 是完整调用档案，人工阅读的材料正文仍在 `drafts`，审核表仍在 `review`。

## 目录

根目录只分三类：

- `onet_download/`：每轮 O*NET 下载的来源和状态记录，原始网页位于 `sources`。
- `occupation_generation/`：按总批次，再按英文职业名与 O*NET 编码分组，内部放 JD 和简历调用。
- `morality_generation/`：按总批次，再按道德维度分组，内部放条目调用。

每个批次名为 `YYYYMMDD_三位累计编号`。三类各自累计，跨日期不重置；已有只准备输入的历史批次也占编号。一次 API 调用不是一个总批次，一批可以有多个职业、数十或数百次调用。

```text
occupation_generation/
└─ 20261125_012/
   ├─ 批次信息.json
   ├─ 调用清单.csv
   └─ Software_Developers_15-1252.00/
      ├─ 016_jd/
      │  ├─ input.json
      │  └─ output.json
      ├─ 017_resume_R01/
      └─ …
```

当前四份 JD 与十六份简历合在 `occupation_generation/20261125_012`，每个职业五项调用。编号从001到020覆盖整批，不代表实际完成先后。道德当前批次为 `morality_generation/20261124_004`，268项只有输入、尚未执行。

## 先看什么

1. 看 `调用清单.csv`：找到任务、状态、输入、输出和当前草稿的位置。路径相对于项目根目录。
2. 想知道模型实际读了什么：打开调用目录的 `input.json`，看 `request.task.messages`。
3. 想知道返回了什么：打开 `output.json`，看 `answer`、`status`、`error_message`。
4. 只读 JD／简历正文：打开清单中的 drafts 文本，或从个人审核表点击“打开材料”。

`批次信息.json` 是总登记表，集中保存阶段计划、参数、调用身份、成功材料对应关系及历史别名。它不是另一次模型输出。公共提示词模板仍在 `prompts`；具体填好的提示词已在 input 中，不再重复保存 prompt.txt 或 request.json。

## 输入、输出和草稿

- `input.json`：包含完整请求、模型参数、来源和控制设定。`context` 是追溯信息，整个档案并非全部作为提示词发送；实际消息在 `request.task.messages`。
- `output.json`：保存原始接口响应、`answer`、状态、用量及错误信息。流式返回片段可能很多，不代表生成了很多份材料。
- 没有 output 表示只准备过输入；不能当作已经生成材料。
- `status=ok` 表示通过现有程序检查，不等于人工审核通过。
- JD／简历成功回答的 `answer` 原样写入 drafts 的 TXT。批准 JD 时才执行约定的公告边界提取；简历批准时逐字节复制。道德草稿维持 JSON。

失败目录以 `_fail` 结尾，重试另建 `_retry001`、`_retry002` 等目录；重试失败再加 `_fail`。普通首次调用无 a01 后缀。只有明确指定 `--retry-failed` 才会重试失败记录，原始输入输出不覆盖。

`CARE_00101` 仍表示旧规则中的来源条目与改编变体；开头的三位数字是批内任务序号，二者含义不同。

## 运行与引用

同一轮 JD 和简历使用相同 `--run-id`，简历用 `--jd-run-id` 明确引用已生成的 JD。后续独立的一轮简历可以使用新批次，再引用旧 JD；不向已有阶段悄悄追加不同输入。

```powershell
# 预览当前批次，不调用模型
.\.venv\Scripts\python.exe -X utf8 -B material_preparation/run_material_generation.py --task jd --run-id 20261125_012
.\.venv\Scripts\python.exe -X utf8 -B material_preparation/run_material_generation.py --task resume --run-id 20261125_012 --jd-run-id 20261125_012 --levels medium low --count 2

# 配套批次包含两类材料，批准时明确类型；默认仅预览
.\.venv\Scripts\python.exe -X utf8 -B material_preparation/approve_materials.py --run-id 20261125_012 --task jd
.\.venv\Scripts\python.exe -X utf8 -B material_preparation/approve_materials.py --run-id 20261125_012 --task resume

# 只核验历史迁移，不调用模型
.\.venv\Scripts\python.exe -X utf8 -B material_preparation/migrate_result_layout.py --verify
.\.venv\Scripts\python.exe -X utf8 -B material_preparation/verify_result_layout.py
```

新一轮输入、模型参数或模板变化时，使用新的总批次号，不能覆盖现有同名草稿。一次新的独立生成工作应创建新批次。

## 历史记录

旧 input／output 保持原始字节，内部的旧 run_id 和旧路径不被改写。`config/results_layout.json` 保存完整的新旧映射和指纹，读取时解析这些历史引用。新的批次信息和清单使用新位置。

旧计划、重复的 prompt／request、原清单和早期两次 AI 简历审读保存在所属批次的 `历史附档.zip`；它们不是当前生成材料。旧审核截图移入 `review/历史预览图片`。迁移前完整备份位于项目外，迁移核验会逐份检查全部2611份历史文件及70份API输出。

无需为了读取历史记录把旧目录恢复到项目中；也不要手工改原始 JSON 来配合新文件夹名。实验1、2、3的结果结构继续保持原样。

O*NET资料校验始终严格检查原始网页和结构化来源。当前生成模板可以有后续版本，校验器会明确报告它相对旧导出的差异；如需同时要求模板与旧导出一致，可加`--strict-templates`。每次调用实际使用的模板内容以不可改写的input为准。

如需取回完整旧布局，可运行 `migrate_result_layout.py --recover-to <项目外空目录>` 先预览，再加 `--execute` 写入恢复副本。该操作不覆盖当前项目，也不修改迁移后的记录。
